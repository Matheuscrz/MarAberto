# ADR-019: App mobile com Capacitor sobre o PWA existente

- Status: **Aceito (2026-11-11)** — decisão de empacotamento **aplicada no repositório**: Capacitor **8.6.0** instalado em `web/`, `android/` gerado e sincronizado, plugins de geolocalização/notificação/keep-awake integrados por adaptadores em `shared/`, build web e build nativo (`--mode capacitor`) verdes, **APK debug gerado** (`web/android/app/build/outputs/apk/debug/app-debug.apk`) e **sessão do WebView resolvida** por HTTP nativo + jar de cookies (`CapacitorHttp` + `CapacitorCookies`), sem alterar o backend nem afrouxar o `SameSite=Strict`. Falta o teste em aparelho real.
- Contexto: o frontend é **um único app React** em `web/` (ADR-015), já PWA instalável e com as três áreas operacionais funcionando contra o backend real. Existe um projeto **Flutter** iniciado em `mobile/` (`android/`, `ios/`, `lib/`), criado antes desta decisão, porém sem paridade com o app web — reescrever mapa, fila do SOS, plantão e ocorrências em Flutter levaria semanas e criaria duas bases de UI para manter. Ao mesmo tempo, o PWA tem limites no celular: no iOS ele só é "instalável" pelo Safari, não há presença em loja, Web Push com app fechado é frágil e o service worker **não é suportado no WKWebView** (e no Android WebView depende do hostname). O órgão precisa de um **APK instalável agora**, sem esperar o app nativo "de verdade".
- Decisão:
  - **O app mobile é o próprio `web/` empacotado com Capacitor 8 (WebView).** Não existe fork, build paralelo nem segunda base de UI: a mesma aplicação React roda em navegador, PWA instalada e app nativo. Correção de tela entra uma vez e vale para os três.
  - **O projeto nativo mora em `web/`**: `web/capacitor.config.ts` (`appId: org.maraberto.app`, `appName: MarAberto`, `webDir: dist`), `web/android/` gerado agora e `web/ios/` gerado **depois**, em macOS com Xcode (no Linux o Capacitor até cria a pasta, mas o build e o `pod install` exigem macOS).
  - **`mobile/` (Flutter) fica congelado e intocado por enquanto.** Não entra em build, CI, lint ou documentação de arquitetura como referência vigente. A retomada é planejada para o app "mais trabalhado" (mapa nativo, rastreamento em segundo plano, push, presença em loja) — quando essa decisão vier, ela substitui esta ADR, não a duplica.
  - **O código web não conhece Capacitor diretamente.** Detecção de plataforma e adaptação ficam em um único módulo de `shared/` (ex.: `shared/lib/platform.ts`), com a implementação web como padrão; nenhuma feature importa `@capacitor/*` direto. Isso preserva as regras de fronteira da ADR-015 e mantém o PWA funcionando sem os plugins.
  - **A sessão continua com cookie `HttpOnly`** (ADR-009 / §13.1): o refresh **não** vai para `localStorage`/`sessionStorage` nem para `@capacitor/preferences`. O transporte escolhido é **`CapacitorHttp` + `CapacitorCookies`**: as chamadas do app saem pelo HTTP nativo (sem CORS, porque o backend não abre origem cruzada) e o plugin core `CapacitorCookies` registra o `CookieHandler` do processo com o `CookieManager` do WebView, então o `HttpURLConnection` por trás do `CapacitorHttp` envia o cookie no refresh/logout e guarda o `Set-Cookie` do login **sem o JavaScript tocar no valor** e com persistência entre reinícios do app. O `SameSite=Strict` do backend fica **intacto**; a alternativa de origem móvel com `SameSite=None` + CORS com credenciais não foi necessária.
  - **`VITE_API_BASE_URL` passa a ser obrigatório no build nativo.** No navegador o padrão é "mesma origem" via proxy; no app a origem é `https://localhost` (Android) / `capacitor://localhost` (iOS), então caminho relativo aponta para o próprio WebView. O build do app usa URL absoluta **HTTPS** do backend.
  - **O service worker não é usado no nativo.** `offline.html`, cache do `sw.js`, prompt de instalação e notificação via `ServiceWorkerRegistration.showNotification` não valem (ou não são confiáveis) dentro do WebView. No app: fallback offline é o próprio bundle local; o alerta do SOS usa **notificação nativa** (`@capacitor/local-notifications` para o alerta em primeiro/segundo plano e, na sequência da ADR-018 item 6, `@capacitor/push-notifications` para app fechado), mantendo a sirene WebAudio e o popup como estão.
  - **Plugins instalados e integrados por adaptador:** `@capacitor/geolocation` (posição pontual do plantão, SOS e cadastro de posto/base), `@capacitor/local-notifications` (notificação do SOS no WebView, que não tem service worker) e `@capacitor-community/keep-awake` (tela ligada durante o atendimento). `browser` **não** foi necessário: o `Bridge` do Capacitor já entrega `http(s)`/`tel:` ao app externo, então a rota no Google Maps e o "Ligar 193" continuam funcionando. `camera` fica para quando houver captura de foto (hoje a foto de posto/base é uma URL). `push-notifications` entra na sequência da ADR-018 item 6. `@capacitor/preferences` **não** é usado para token nem coordenada.
  - **Endurecimento obrigatório no projeto nativo:** `android:allowBackup="false"` (o backup do Android levaria o storage do WebView, incluindo qualquer cache de sessão), sem `usesCleartextTraffic` em release, permissões declaradas só as necessárias (`ACCESS_COARSE/FINE_LOCATION`, câmera, notificações) e CSP por `<meta http-equiv="Content-Security-Policy">` no `index.html` — no app **não existe Nginx** para aplicar a CSP da §13.3.
  - **Distribuição:** APK/AAB assinado para o órgão e, quando houver conta, Play Store (`targetSdk` 36 já é o gerado). Para iOS, avaliar App Store x **Apple Business Manager / app não listado**, porque um app majoritariamente WebView corre risco na diretriz 4.2 (minimum functionality) — o mitigador é usar recursos nativos de verdade (GPS, notificações, câmera, deep links), que já são requisitos do produto.
- Alternativas:
  - **Só PWA instalável, sem app** (rejeitada): no iOS a instalação é manual pelo Safari, não há loja, push com app fechado é frágil e o service worker não funciona no WKWebView. Não atende "instalar o app no aparelho do guarda-vidas".
  - **Continuar direto no Flutter agora** (rejeitada para esta etapa): reescrever mapa (MapLibre), fila do SOS, plantão, ocorrências e as três áreas por perfil duplica a UI e atrasa o uso em campo. `mobile/` fica para a fase seguinte.
  - **Capacitor com `server.url` apontando para o site público** (rejeitada): o app vira um "site embrulhado" — depende de rede para abrir, perde o bundle local, conflita com CSP/service worker do site e piora a avaliação das lojas.
  - **React Native / Expo** (rejeitada): reescrita completa do frontend, mesmo custo do Flutter sem aproveitar o que já está pronto.
  - **Cordova** (rejeitada): projeto em modo de manutenção; Capacitor é o sucessor mantido, com plugins oficiais e configuração em JSON.
  - **WebView "na mão" (Android Activity + iOS WKWebView)** (rejeitada): reimplementa permissões, file chooser, deep links, cookies e sincronização de assets — exatamente o que o Capacitor entrega pronto.
- Consequências:
  - **Ganho:** APK em dias, uma base de código, deploy do web e do app pelo mesmo build; o guarda-vidas passa a ter ícone na tela inicial, notificação nativa e GPS com permissão de app.
  - **Limite honesto:** WebView não é app nativo. Desempenho do mapa em aparelho fraco, consumo de bateria do GPS e o comportamento de segundo plano precisam ser medidos em campo; nada de rastreamento contínuo (RN17 continua valendo).
  - **Duplicidade temporária no repositório:** `mobile/` Flutter parado ao lado de `web/android/`. Enquanto congelado, não é referência de arquitetura nem entra no CI; a limpeza (ou a retomada) é uma decisão explícita futura.
  - **Segurança:** a superfície cresce (WebView + plugins + backup + permissões). Os itens de endurecimento acima são pré-requisito do primeiro APK distribuído, junto do item já existente de não logar coordenada.
  - **Trabalho novo que esta ADR cria:** ~~resolver o transporte de sessão no WebView~~ (**feito**: HTTP nativo + jar de cookies), evoluir os adaptadores nativos (câmera, push, links externos), gerar ícone e splash a partir dos assets atuais — hoje são os **padrões do Capacitor**, porque não há arte de marca —, configurar assinatura e versionamento (`versionCode`/`versionName`) e validar em aparelho real.
  - **CI:** o job atual continua só backend. Build Android entra como job opcional (JDK 21 + SDK) depois que o primeiro APK estiver estável; iOS fica fora do CI hospedado (exige macOS).
- Aplicação no repositório (2026-11-11):
  - Instalado em `web/`: `@capacitor/core` e `@capacitor/android` (dependências), `@capacitor/cli` (devDependency); configuração em **`capacitor.config.ts`** (o CLI gera `.ts` quando o projeto é TypeScript, não `.json`).
  - `npx cap init MarAberto org.maraberto.app --web-dir dist` e `npx cap add android` rodados **dentro de `web/`**. O `cap init` aceita os argumentos posicionais e `--web-dir` sem prompt; `--no-interactive` **não existe** no CLI 8 e falha com `unknown option`.
  - O projeto gerado veio com `minSdkVersion 24`, `compileSdkVersion`/`targetSdkVersion` **36**, AGP **8.13**, Gradle **8.14.3** e um `AndroidManifest.xml` com **apenas** `INTERNET`; foram adicionadas `ACCESS_COARSE/FINE_LOCATION` e `uses-feature android.hardware.location.gps required="false"`, além de `android:allowBackup="false"` (o padrão era `true`).
  - `android/.gitignore` já ignora `build/`, `.gradle/`, `local.properties`, `app/src/main/assets/public` e `app/src/main/assets/capacitor.config.json`, então `android/` é versionado sem lixo de build.
  - **Código adaptado:** `shared/lib/platform.ts` (único módulo, junto de `native.ts`, que importa `@capacitor/*`), `shared/lib/native.ts` (adaptadores dos plugins: posição pontual com permissão, notificação persistente do SOS com canal `sos`, cancelamento e keep-awake), `shared/lib/geolocation.ts` (usa o plugin no nativo e a API do navegador no PWA; `getDevicePosition` virou `async`, e as telas — `MapView`, `SosPage`, `OperatorOccurrencesPage`, `StationRegistry` — deixaram de chamar `navigator.geolocation` direto), `features/operator/lib/sos-alarm.ts` (sirene WebAudio, permissão de notificação do plugin com cache em memória e wake-lock nativo), `shared/lib/pwa.ts` (não registra service worker no nativo), `shared/lib/api-client.ts` (todas as chamadas do app saem por `executeNative`, com timeout explícito; login/refresh/logout trocam o cookie de refresh pelo jar nativo — ver abaixo) e `vite.config.ts` com `--mode capacitor`: exige `VITE_API_BASE_URL` absoluto em HTTPS, injeta a CSP por `<meta>` (origem da API/WS e, se houver, dos PMTiles) e mantém o build web inalterado. Scripts `build:app`, `cap:sync` e `cap:open` em `web/package.json`; `.env.capacitor.example` documenta o build nativo.
  - **Verificado:** `npm run build`, `npm run lint`, `VITE_API_BASE_URL=https://… npm run build:app`, `npm run cap:sync` (3 plugins reconhecidos: geolocation 8.2.4, local-notifications 8.3.1 e keep-awake 8.0.1) e `./gradlew assembleDebug` verdes; o `dist/index.html` do modo nativo contém a CSP com `connect-src 'self' https://<backend> wss://<backend>` e os assets (incluindo `maplibre-gl-worker-*.mjs`) aparecem em `android/app/src/main/assets/public`.
  - **Worker do MapLibre:** conferido no fonte do Capacitor 8 (`WebViewLocalServer.getMimeType`) que `.js` **e** `.mjs` são servidos como `application/javascript`. Não é preciso renomear o worker como o Nginx exigia com `default_type`.
  - **APK debug gerado (2026-11-11):** `web/android/local.properties` aponta `sdk.dir` para o Android SDK local (platform 36 + build-tools 35/36); o build roda com `JAVA_HOME` no Temurin **21** (o wrapper é Gradle 8.14.3). O AGP baixou o Build-Tools 35 automaticamente, então não foi necessário fixar `buildToolsVersion`. Saída em `web/android/app/build/outputs/apk/debug/app-debug.apk` (assinatura debug, distribuível só para teste). iOS exige macOS + Xcode.
  - **Sessão no WebView (implementada em 2026-11-11):** `shared/lib/api-client.ts` usa `executeNative` para **todas** as chamadas quando `isNativeApp()` — `CapacitorHttp.request` direto (sem o patch global de `window.fetch`, que esconderia o `Set-Cookie` e ignoraria os timeouts do cliente), com `connectTimeout`/`readTimeout`. O cookie de refresh **não passa pelo JS**: o plugin core `CapacitorCookies`, carregado no boot do bridge, faz `CookieHandler.setDefault(CapacitorCookieManager)`, e esse manager lê/grava no `CookieManager` do WebView (persistente em disco). Como o `HttpURLConnection` usado pelo `CapacitorHttp` consulta o `CookieHandler` do processo, o cookie `HttpOnly; Secure; SameSite=Strict` do backend é enviado no refresh/logout e atualizado no login **automaticamente** — o que também explica por que `CapacitorCookies.getCookies` não serve para ler o refresh (no Android ele devolve `document.cookie`, onde cookie `HttpOnly` não aparece). O access token continua **só em memória**, o backend **não mudou** (`SameSite=Strict`, sem CORS) e não existe `session-cookie.ts` nem qualquer token em storage web.
  - **Requisito de implantação para o app:** o handshake STOMP do console carrega `Origin: https://localhost` (Android) ou `capacitor://localhost` (iOS). O backend precisa listar essas origens em `REALTIME_ALLOWED_ORIGINS` (`maraberto.realtime.allowed-origins`), porque `setAllowedOriginPatterns` recusa origem não listada — é configuração de ambiente, não abertura de CORS na API.
  - **Não implementado ainda:** plugins de câmera/push/links externos, ícone/splash próprios (hoje são os padrões do Capacitor), `versionCode`/keystore de release, build de verificação em aparelho real **e** o item 6 da ADR-018 (Web Push com o app fechado).
